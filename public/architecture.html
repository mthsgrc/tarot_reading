Snapshot

A client-only React SPA with two systems: Thoth Tarot through Thelema and the Golden Dawn, and a local Chaos Magic toolkit. There is no backend, database, authentication, LLM, or runtime API. The deck, spreads, and interpretation rules are static data plus deterministic TypeScript logic; saved readings, shareable links, servitors, paradigms, and magical records are encoded or stored locally.

Architecture

The project is a layered front end with a strict practical boundary: domain and data are pure, pages orchestrate, components render, and lib owns browser side effects.

Application tree index.html └── src/main.tsx ├── global CSS └── app/App.tsx └── HashRouter ├── ScrollToTop └── Routes └── app/Layout.tsx (system-aware shell + accent) ├── header / navigation / footer ├── RouteErrorBoundary + Suspense └── <Outlet /> ├── HomePage (eager chooser) ├── ReadingPage (eager, /thelema) ├── ChaosHomePage (lazy, /chaos) ├── SigilPage (lazy, /chaos/sigil) ├── GnosisPage (lazy, /chaos/gnosis) ├── CutUpPage (lazy, /chaos/cut-up) ├── ServitorsPage (lazy, /chaos/servitors) ├── ParadigmPage (lazy, /chaos/paradigms) ├── RecordPage (lazy, /chaos/record) ├── WorkingPage (lazy, /chaos/working) ├── SourcesPage (lazy, /chaos/sources) ├── LibraryPage (lazy) ├── StudyPage (lazy) ├── JournalPage (lazy) ├── CardPage (lazy) ├── TraditionPage (lazy) └── NotFoundPage (lazy)

The main dependency direction is one-way: pages → domain/data/lib/components. Components do not import pages, and domain modules do not import React.

Legacy routes (/library, /study, /journal, /tradition, /cards/:cardId) redirect to their canonical /thelema paths and preserve search parameters. Old #/?... share links are forwarded by HomePage to #/thelema?....

The Chaos toolkit index is generated from src/app/chaosTools.ts. The home grid and the Sources page read the same list. All eight Chaos routes are lazy-loaded and keep their state in memory or local storage.

The reading page stays in the entry bundle because it is the main Thelema route and every share link opens there. Layout wraps pages in a RouteErrorBoundary keyed by pathname and a Suspense fallback. It derives the active system from the path, swaps brand/navigation/footer content, and sets data-system and data-accent on <html>. The Chaos accent lives in Layout state, so it survives route changes.

How the files talk

Application startup

Boot sequence index.html → src/main.tsx → imports styles/tokens.css, base.css, chaos.css, print.css → renders <App /> → App creates HashRouter and route table → Layout renders the system-aware shell and <Outlet /> → selected page renders

ScrollToTop listens to router location changes and scrolls on navigation (src/app/App.tsx:32).

Reading flow

Main feature path ReadingPage → data/spreads.ts spread definitions and defaults → domain/deck.ts shuffle and draw → components/SpreadPicker choose spread → components/SpreadBoard → components/TarotCardView → components/CardImage / CardBack → domain/reading/interpret.ts once all cards are revealed → components/ReadingInterpretation → components/CardDetailDialog → components/CardDetail → CardImage + TreeOfLifeDiagram

ReadingPage is the main state owner: spread, question, shadow flag, lens, depth, drawn cards, reveal state, dialog index, clipboard status, and journal status. Children receive values and callbacks; they do not reach into storage or the URL directly.

  • Draw → handleStart calls drawCards and stores the result in drawn.
  • Reveal → updates the matching card's revealed flag.
  • Open card → stores openIndex; CardDetailDialog renders the selected DrawnCard.
  • Interpret → once every card is revealed, a memo calls interpretReading and passes the result to ReadingInterpretation.
  • Copy reading → formatReading converts the interpretation to plain text.
  • Print → window.print(); print.css and component print rules take over.

Interpretation engine

src/domain/reading/interpret.ts:19 is the single pure entry point:

Domain pipeline ReadingInput → buildFacts counts, arcana, suits, elements, orientations, repeated numbers, shared Sephiroth, card-to-station resonances, inferred/explicit lens → buildFactInsights + buildRelationInsights element, major, court, shadow, number, Sephira, resonance, keyword observations, spread-specific card-to-card relations → selectInsights sort by weight, deduplicate, cap by depth, limit each insight kind → synthesis headline, overview, per-position paragraphs, spread-specific movement, one action → ReadingInterpretation
File Role
facts.ts Builds the factual model of the draw
relations.ts Compares cards and builds spread-specific relations
notices.ts Creates, scores, and caps pattern observations
synthesis.ts Turns facts and notices into prose
language.ts Labels, lens frames, element voices, element relations
positions.ts Position intros, Tree triads, shared element list
text.ts Text helpers, hashing, deterministic phrase selection
format.ts Plain-text export
types.ts Reading input/output types and shared lens/depth constants
share.ts Share-link encoding, decoding, validation
journal.ts Journal validation, serialization, deduplication
interpret.ts Pipeline composition

Determinism matters here: the draw is encoded, and phrase variants are selected from a hash of the spread and cards plus a salt (pickVariant), so the same draw produces the same reading.

Share-link loop

Share state ReadingPage state → buildShareParams → buildShareUrl → clipboard URL hash → readSharedReading → validates version, spread, cards, orientations, duplicates, lens, depth, question length → ReadingPage state

readSharedReading returns null for malformed links. ReadingPage handles that by returning to setup and showing an error, rather than rendering partial data. Removing share parameters also resets stale reading state.

Share links are self-contained. They contain the spread, card IDs, orientations, optional question, shadow flag, lens, and depth. Nothing is uploaded.

Journal loop

Local persistence ReadingPage → buildShareParams → lib/journalStorage.saveJournalEntry → domain/reading/journal.upsertJournalEntry → validates through readSharedReading → serialize → localStorage JournalPage → loadJournal → parseJournal → re-validates each stored entry through readSharedReading → renders entries as links: /?<params>&j=1 → opens the same ReadingPage share-link path

The journal deliberately reuses the share format instead of inventing a second serialization format. Entries store the encoded parameters, timestamp, and stable ID. Cross-tab changes are detected with a storage event listener in JournalPage.

Library and card page

Deck browsing LibraryPage → ALL_CARDS → module-level CARD_SEARCH_WORDS index → local search/arcana/suit/element filters → links to /thelema/cards/:cardId → CardPage → useParams → getCardById → CardDetail → previous/next card pager from ALL_CARDS

The search index is precomputed once at module load, so typing does not rebuild every card's searchable text on each keystroke.

Study quiz

Correspondence drill StudyPage → domain/study.ts createStudyQuestion → ALL_CARDS + Tree/Sephira metadata → one topic for the card kind → four shuffled, unique options and an explanation → local question, selected answer, and in-session score → links to /cards/:cardId after answering

createStudyQuestion accepts an injected RandomSource: the page uses Math.random, and tests use seededRandom to prove determinism and full topic coverage. There is no saved score or URL state, so leaving the page resets the quiz.

Tradition page

Static study content TraditionPage → data/tradition.ts Sephira themes, number notes, element practices → domain/tree.ts Sephiroth and element metadata → TreeOfLifeDiagram visual Tree with optional highlight

TreeOfLifeDiagram also imports the major cards so each path can be drawn and labelled from the card's path metadata.

Chaos toolkit

Tools and storage SigilPage → deterministic mirrored glyph from surviving consonants │ GnosisPage → deadline-based attention timer │ CutUpPage → seeded Fisher-Yates shuffle │ ServitorsPage → localStorage records (50 cap) │ ParadigmPage → one open experiment plus 30-record history │ RecordPage → shared log (100 cap) │ WorkingPage → workingToRecordDraft → addStoredRecord │ SourcesPage → static context, safety, and references

The Chaos domain modules own validation, deterministic geometry, seeded shuffles, date math, and record shapes. Browser adapters in src/lib own localStorage, id generation, caps, and storage-event refreshes. The Magical Record adapter is deliberately reusable: the Working Composer writes into the same log with the kind set to working. The Sources page is static reference content in src/data/chaosSources.ts; it keeps ritual and banishing as context rather than guided exercises.

Data model

Core types live in src/domain/types.ts:

  • Element, Suit, CourtRank, NumberRank, Sephira, Orientation
  • MajorCard | MinorCard | CourtCard → TarotCard
  • Spread, SpreadPosition, SpreadLayout
  • DrawnCard = card + position + orientation + revealed flag

Card content lives under src/data/cards/, split by suit:

  • majors.ts — 22 Atu
  • wands.ts, cups.ts, swords.ts, disks.ts — 14 each
  • index.ts — combines them into ALL_CARDS and CARD_BY_ID

src/data/cards.test.ts enforces deck integrity: 78 unique cards, 22 majors, four suits of 14, unique Hebrew letters, unique Tree paths, valid ranks, valid Sephiroth, content completeness, and the existence of AVIF/WebP art for every card.

Assets

Original artwork lives in images/ and is not formatted by Prettier. scripts/optimize-images.mjs uses ImageMagick to generate:

  • public/images/cards/<card-id>.avif
  • public/images/cards/<card-id>.webp
  • public/images/back-cover.avif
  • public/images/back-cover.webp

CardImage renders a <picture> with AVIF first, WebP fallback, and a styled placeholder on failure. Image URLs use import.meta.env.BASE_URL, so they work from a GitHub Pages subpath.

Styling

  • src/styles/tokens.css — colors, semantic accent tokens, fonts, spacing, radii, shadows.
  • src/styles/base.css — reset, typography, buttons, panels, focus, skip link, visually-hidden utilities.
  • src/styles/chaos.css — black-and-white Chaos palette, data-accent colour map, and system-scoped body/type overrides.
  • src/styles/print.css — flips both dark themes to ink-on-paper, hides navigation and dialogs, and controls page breaks.
  • Each component/page has a colocated .module.css for scoped layout and print rules.

There is no CSS-in-JS runtime and no utility framework.

Two-system theme

Layout chooses a system from the pathname (src/app/paths.ts) and writes data-system="home|thelema|chaos" plus data-accent="..." to <html>. Shared components consume semantic tokens such as --color-accent, --line, and --color-surface, so the same buttons and panels work in both systems.

The Chaos accent is one of the ids in src/app/chaosAccent.ts; src/styles/chaos.css maps each id to RGB channels and derives soft, focus, and glow values. The picker uses Math.random() once when Layout mounts, and New signal calls it again while excluding the current colour. A test reads chaos.css?raw and enforces AAA contrast for every accent against the black shell.

The accessibility audit renders real pages with axe under WCAG A/AA tags, but explicitly disables color contrast because jsdom has no paint or layout. Real-browser contrast and layout checks remain a manual step.

CI (.github/workflows/ci.yml) runs npm run verify on push to master and pull requests. Deployment (.github/workflows/deploy.yml) reruns verification, builds dist/, and publishes to GitHub Pages.

Architectural strengths

  • Clear separation between content, domain logic, presentation, and browser side effects.
  • Deterministic interpretation engine with no network or runtime randomness during rendering.
  • Share links and journal entries use one validated encoding format.
  • The eight Chaos tools share validation and storage patterns where useful; the Working Composer writes into the same Magical Record format.
  • Strong data-integrity and domain test coverage.
  • Injected randomness keeps quiz generation testable without a live source.
  • Lazy-loaded secondary routes with route error recovery.
  • Accessibility is treated as part of the component and API design, not an afterthought.

Notable coupling and risks

  • ReadingPage is still the largest orchestration point, owning setup, reading, URL sync, clipboard, journal, and dialog state. The planned M8 split into ReadingSetup, ReadingResult, and a reducer or hook has not been done.
  • The reading engine has spread-specific branches in relations.ts, notices.ts, and synthesis.ts, all keyed by position IDs. This is readable, but adding a spread requires coordinated updates in several modules.
  • domain/deck.ts imports ALL_CARDS directly, even though drawCards also accepts an injected deck. Domain modules therefore depend on static data rather than being fully content-agnostic.
  • HashRouter keeps GitHub Pages deployment simple, but URLs live after #, which is less SEO-friendly. New share links use #/thelema?...; the old #/?... form survives only as a redirect.
  • Color contrast and visual layout still need real-browser verification; the jsdom axe pass cannot judge them.
  • Journal and Chaos records live only in localStorage. Clearing browser data removes them, and there is no export or backup yet.
